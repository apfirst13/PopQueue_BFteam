## A.1 Stakeholder Problem, Context และ Walkthrough Scenario

### 1. ปัญหาและบริบท (Problem & Context)
* **ปัญหาของ Stakeholder:** ร้านจำหน่าย Art Toy (เช่น Pop Mart – Crybaby, Labubu) ประสบปัญหาลูกค้าแออัดบริเวณหน้าสถานีแกะกล่อง เกิดการแซงคิว ความขัดแย้ง และไม่มีหลักฐานลำดับคิวที่โปร่งใสตรวจสอบได้ ขั้นตอน **"เลือกกล่องสุ่มและแกะเช็กการ์ดสดที่เคาน์เตอร์ (Live Unboxing Station)"** ใช้เวลาบริการเฉลี่ยประมาณ 2–3 นาทีต่อราย
* **ระบบ PopQueue:** เป็น **On-site Virtual Waiting Queue** แบบวันเดียวกัน (Single-day Waiting Line) ลูกค้าต้องชำระเงินค่าสินค้าที่เคาน์เตอร์แคชเชียร์หลักของร้านค้าให้เรียบร้อยก่อน จึงนำกล่องมารับบัตรคิวผ่านเว็บแอปพลิเคชัน PopQueue เพื่อรอรับบริการแกะกล่องสด (ระบบ PopQueue ไม่เกี่ยวข้องกับการชำระเงินหรือการซื้อขายสินค้า)

### 2. ตาราง Stakeholders
| Stakeholder | ผลประโยชน์ / ปัญหาที่เผชิญ | บทบาทในระบบ (Role) |
| :--- | :--- | :--- |
| **ลูกค้า / นักสะสม (Collectors)** | ไม่รู้ลำดับคิวที่แน่นอน ไม่อยากยืนรอแออัดหน้าเคาน์เตอร์ ต้องการความโปร่งใสและเป็นธรรม | Collector |
| **พนักงานสถานีแกะกล่อง (Station Staff)** | ต้องการระบบเรียกคิวตามลำดับ ป้องกันลูกค้าแย่งกัน และต้องการกลไกยืนยันตัวตนลูกค้าเมื่อมาถึงหน้าร้านจริง | Box Master |
| **ผู้จัดการร้าน (Store Manager)** | ต้องการตรวจสอบสถิติเวลารอ อัตราลูกค้าไม่มาตามนัด (Sprint 3) และควบคุมการเปิด–ปิดรับคิวแต่ละซีรีส์ | Box Master (สิทธิ์ระดับซีรีส์ – ไม่มี Role Manager แยกใน Baseline) |
| **ผู้ชมหน้าร้าน (Public Viewers)** | ดูหมายเลขคิวที่กำลังให้บริการและจำนวนคิวรอเพื่อประเมินเวลา | Public Viewer (ไม่ต้องล็อกอิน) |

### 3. ลำดับเหตุการณ์การใช้งานจริง (Walkthrough Scenario)
1. **รับตั๋วคิว:** คุณสมชาย (Collector `collector1`) ชำระเงินที่แคชเชียร์เรียบร้อย เดินมาโซน Unboxing เปิดเว็บ PopQueue ล็อกอินด้วยบัญชี Seeded เลือกซีรีส์ *Crybaby Sunset Concert* ระบบออกบัตรคิว **CRY-012**
2. **ตรวจสอบสถานะ:** หน้าจอตั๋วของสมชายแสดงสถานะ `WAITING` พร้อมข้อความ *"เหลืออีก 3 คิวก่อนหน้าคุณ"* โดยหน้าจออัปเดตข้อมูลอัตโนมัติด้วย Short Polling ทุก 3 วินาที
3. **พนักงานเรียกคิว (Call Next):** Box Master (`staff_crybaby`) กดปุ่ม **"Call Next"** ระบบจะผูก `handledByStaffId` และบันทึกเวลา `calledAt` พร้อมเปลี่ยนสถานะเป็น `CALLED` หน้าจอลูกค้าเปลี่ยนเป็นสีส้มแจ้ง *"ถึงคิวแล้ว กรุณามาที่เคาน์เตอร์"* พร้อมตัวนับถอยหลัง 120 วินาที
4. **ยืนยันตัวตนหน้าร้านโดยพนักงาน:** สมชายเดินมาถึงหน้าเคาน์เตอร์ **พนักงานเป็นผู้ตรวจสอบบัตรคิวและกดปุ่ม "Verify & Start Unboxing"** เพื่อเปลี่ยนสถานะเป็น `UNBOXING` (ลูกค้าไม่สามารถกดยืนยันเองได้ เพื่อป้องกันการกดยืนยันระยะไกลโดยไม่อยู่หน้าร้านจริง)
5. **ให้บริการเสร็จสิ้น:** พนักงานแกะกล่องเสร็จสิ้น กดปุ่ม **"Complete"** สถานะเปลี่ยนเป็น `COMPLETED` พนักงานว่างและพร้อมเรียกคิวถัดไป
6. **กรณีลูกค้าไม่มา (Sprint 2):** หากครบ 120 วินาทีแล้วลูกค้าไม่ปรากฏตัว พนักงานกด **"Mark No-Show"** โดย Server ตรวจสอบ `now - calledAt >= 120s` แล้วเปลี่ยนสถานะเป็น `NO_SHOW` (ลูกค้ารับคิวใหม่ได้แต่ต้องไปต่อท้ายแถว)
7. **กรณียกเลิกคิว (Sprint 2):** ลูกค้าสามารถกดยกเลิกตั๋วของตนเองได้ขณะที่ตั๋วยังอยู่ในสถานะ `WAITING`

> **ข้อจำกัดของ Sprint 1 (เปิดเผยตามเกณฑ์):** ใน Sprint 1 ยังไม่มีฟังก์ชัน Cancel และ No-Show หากลูกค้าถูกเรียก (`CALLED`) แล้วไม่มา พนักงานจะติดสถานะให้บริการค้าง (`STAFF_BUSY`) ทางแก้ชั่วคราวในการทดสอบคือคำสั่ง `npm run db:reset-demo`

## A.3 Scope และ Exclusions (ขอบเขตและสิ่งที่ไม่ทำ)

### สิ่งที่อยู่ในขอบเขต (In-Scope)
* ระบบ Virtual Waiting Line แบบวันต่อวันสำหรับหน้าร้าน Art Toy
* การออกเลขคิวต่อเนื่องรายวันแยกอิสระตามซีรีส์ ปลอดภัยต่อสภาวะแย่งชิง (Concurrency Safe)
* การควบคุมสิทธิ์ตาม Role และ Scope ซีรีส์อย่างเคร่งครัดที่ Backend
* วงจรสถานะตั๋วคิวตาม State Machine ที่เคร่งครัด ป้องกันการข้ามขั้น
* การจัดการคิว: Cancel และ No-Show พร้อมการตรวจสอบเวลาที่ Server (Sprint 2)
* หน้าจอแสดงผลคิวสาธารณะหน้าร้าน (Public Display Board) (Sprint 2)
* สถิติประสิทธิภาพการให้บริการรายวันและการเปิด–ปิดรับคิว (Sprint 3)
* การจัดเก็บข้อมูลถาวรบน PostgreSQL Database

### สิ่งที่ไม่ทำและอยู่นอกขอบเขตอย่างชัดเจน (Explicit Exclusions)
1. **การจองนัดล่วงหน้า (Advance Booking):** ไม่อยู่ในขอบเขตตามข้อกำหนดโจทย์ Theme 9 (ให้บริการเฉพาะลูกค้าที่มาหน้าร้านวันเดียวกันเท่านั้น)
2. **ระบบชำระเงินและ Payment Gateway:** ไม่มีการเชื่อมต่อ Payment Gateway หรือการจำลองสถานะชำระเงินใด ๆ เนื่องจากลูกค้าชำระเงินเสร็จสิ้นที่แคชเชียร์หลักของร้านก่อนเข้าสู่ระบบคิว
3. **ระบบขนส่งและพัสดุ (Delivery/Shipping):** รองรับเฉพาะการแกะกล่องสดที่สถานีหน้าร้านเท่านั้น ไม่มีการจัดส่งสินค้า
4. **ระบบสมัครสมาชิกด้วยตนเองและกู้รหัสผ่าน (Self-Registration / Password Recovery):** ใช้งานบัญชีผู้ใช้ที่กำหนดไว้ล่วงหน้า (Pre-seeded Accounts) เท่านั้น
5. **การแจ้งเตือนภายนอกระบบ (External Push Notifications / SMS / LINE):** ใช้ระบบ Short Polling ตรวจสอบสถานะภายในเว็บแอปพลิเคชัน
6. **หน้าจอเพิ่ม/ลบซีรีส์สินค้า (CRUD Series UI):** ซีรีส์สินค้าถูกกำหนดผ่านฐานข้อมูล Seed (ยกเว้นปุ่มเปิด–ปิดรับคิวของ Box Master ใน Sprint 3)

## A.5 Business Rules (BR-01 ถึง BR-09) และ State Transition Table

### 1. กฎทางธุรกิจ (Business Rules)
| ID | กฎทางธุรกิจ (ข้อกำหนดระดับโดเมนที่ต้องบังคับใช้อย่างเข้มงวด) | Sprint |
| :---: | :--- | :---: |
| **BR-01** | **Safe Sequential Numbering:** หมายเลขคิวของแต่ละซีรีส์ต้องเริ่มต้นที่ 1 ในแต่ละวัน เพิ่มขึ้นทีละ 1 อย่างต่อเนื่อง ไม่ซ้ำซ้อน ไม่ข้ามเลข และรีเซ็ตใหม่ทุกเที่ยงคืนตามเวลาประเทศไทย (UTC+7) ตั๋วที่ออกจากคิวแล้ว (Complete, Cancel, No-Show) จะไม่ถูกนำเลขกลับมาใช้อีก | 1 |
| **BR-02** | **Single Active Ticket per User:** ผู้ใช้งาน Collector 1 คน สามารถมีตั๋วคิวสถานะ Active (`WAITING`, `CALLED`, `UNBOXING`) ได้ไม่เกิน 1 ใบในระบบพร้อมกันทั้งระบบ (บังคับด้วย Partial Unique Index บน Database) | 1 |
| **BR-03** | **Strict State Lifecycle:** วงจรสถานะของตั๋วต้องเป็นไปตามลำดับ `WAITING` → `CALLED` → `UNBOXING` → `COMPLETED` เท่านั้น ห้ามข้ามขั้นตอนหรือย้อนกลับสถานะ (ใน Sprint 2 รองรับ `WAITING` → `CANCELLED` และ `CALLED` → `NO_SHOW`) | 1 |
| **BR-04** | **Role & Ownership Enforcement:** Collector ไม่มีสิทธิ์เรียกใช้งาน Staff Counter Endpoint (HTTP 403) และดูได้เฉพาะตั๋วของตนเอง; Box Master ไม่มีสิทธิ์เรียกใช้งานฟังก์ชันของ Collector เช่น การกดรับคิวหรือ my-ticket (HTTP 403) | 1 |
| **BR-05** | **Authorized Series Scope:** Box Master สามารถดำเนินการ Call Next, Verify & Start, Complete และ No-Show ได้เฉพาะซีรีส์ที่ตนได้รับมอบหมายเท่านั้น หากข้ามซีรีส์ระบบต้องปฏิเสธด้วย HTTP 403 `FORBIDDEN_SERIES` | 1 |
| **BR-06** | **Single Active Service per Staff:** พนักงาน Box Master 1 คน สามารถมีตั๋วคิวที่กำลังให้บริการ (`CALLED` หรือ `UNBOXING`) ได้ไม่เกิน 1 ใบพร้อมกัน (บังคับด้วย Partial Unique Index บน Database) | 1 |
| **BR-07** | **Handler-Only Verification:** เฉพาะ Box Master คนที่กดเรียกคิวนั้น (`handledByStaffId`) เท่านั้นที่มีสิทธิ์กด Verify & Start และ Complete (พนักงานคนอื่นในซีรีส์เดียวกันจะถูกปฏิเสธด้วย HTTP 403 `FORBIDDEN_NOT_HANDLER`) และลูกค้าไม่สามารถกดเริ่มเองได้ | 1 |

### 2. ตารางวงจรสถานะคิว (State Transition Table)
| จากสถานะ (From) | การกระทำ (Action) | ผู้กระทำ (Actor) | ไปยังสถานะ (To) | รหัสข้อผิดพลาดหากละเมิดกฎ | Sprint |
| :---: | :--- | :---: | :---: | :--- | :---: |
| `[None]` | Join Queue (รับบัตรคิว) | Collector | `WAITING` | `DUPLICATE_ACTIVE_QUEUE` (409), `SERIES_CLOSED` (409), `RESOURCE_NOT_FOUND` (404), `FORBIDDEN_ROLE` (403) | 1 |
| `WAITING` | Call Next (เรียกคิวถัดไป) | Box Master (ซีรีส์ตน) | `CALLED` | `STAFF_BUSY` (409), `FORBIDDEN_SERIES` (403), `EMPTY_QUEUE` (404) | 1 |
| `CALLED` | Verify & Start (เริ่มแกะกล่อง) | Box Master (ผู้ Call) | `UNBOXING` | `INVALID_STATE_TRANSITION` (400), `FORBIDDEN_SERIES` (403), `FORBIDDEN_NOT_HANDLER` (403) | 1 |
| `UNBOXING` | Complete (ให้บริการเสร็จสิ้น) | Box Master (ผู้ Call) | `COMPLETED` | `INVALID_STATE_TRANSITION` (400), `FORBIDDEN_SERIES` (403), `FORBIDDEN_NOT_HANDLER` (403) | 1 |
| `WAITING` | Cancel (ยกเลิกคิว) | Collector (เจ้าของ) | `CANCELLED` | `INVALID_STATE_TRANSITION` (400), `FORBIDDEN_OWNERSHIP` (403) | 2 |
| `CALLED` | Mark No-Show (ลูกค้าไม่มา) | Box Master (ผู้ Call) | `NO_SHOW` | `NO_SHOW_EARLY_REJECT` (400), `FORBIDDEN_NOT_HANDLER` (403) | 2 |

*หมายเหตุ: คู่การเปลี่ยนสถานะอื่นทั้งหมดที่ไม่ได้ระบุไว้ในตาราง (เช่น `CALLED` → `COMPLETED`, `WAITING` → `UNBOXING`, หรือการเปลี่ยนสถานะออกจาก `COMPLETED`) จะถูกปฏิเสธด้วย HTTP 400 `INVALID_STATE_TRANSITION` เสมอ*

## A.7 Assumptions และ Constraints (A-01 ถึง A-07)

* **A-01 (Timezone Dependency):** ข้อมูลวันที่ของคิว (`queueDate`) คำนวณตามเขตเวลาประเทศไทย `Asia/Bangkok (UTC+7)` เสมอ หมายเลขคิวเริ่มต้นนับ 1 ใหม่ทุกเที่ยงคืนเวลาไทย โดยการคำนวณในโค้ดต้องไม่ขึ้นกับ Local Timezone ของเครื่องโฮสต์หรือเซิร์ฟเวอร์ Cloud Run
* **A-02 (Seeded Series Configuration):** ระบบจัดเตรียมข้อมูลเริ่มต้น 3 ซีรีส์ ได้แก่:
  1. `CRY` – Crybaby Sunset Concert (เปิดรับคิว `isActive = true`)
  2. `LAB` – Labubu Macaron (เปิดรับคิว `isActive = true`)
  3. `SKP` – Skullpanda Closed Demo (**ปิดรับคิว** `isActive = false` จัดเตรียมไว้เพื่อทดสอบกฎ BR-09 โดยเฉพาะ)
* **A-03 (Pre-seeded User Accounts):** ระบบเข้าสู่ระบบด้วย Username (ไม่ใช่ Email) และรหัสผ่านถูกโหลดผ่าน Environment Variable เท่านั้น (ไม่มีการฮาร์ดโค้ดรหัสผ่านลงใน Git):
  * `collector1` ถึง `collector6` (Role: `COLLECTOR`): จัดเตรียม 6 บัญชีเพื่อให้ผู้ทดสอบ/UAT สามารถทดสอบได้หลายรอบอย่างต่อเนื่องใน Sprint 1
  * `staff_crybaby` (Role: `BOX_MASTER`, ซีรีส์: `CRY`): พนักงานหลักประจำซีรีส์ Crybaby
  * `staff_crybaby2` (Role: `BOX_MASTER`, ซีรีส์: `CRY`): พนักงานคนที่สองประจำซีรีส์ Crybaby ใช้ทดสอบการถูกปฏิเสธเมื่อไม่ใช่ผู้เรียก (`FORBIDDEN_NOT_HANDLER`) และทดสอบการเรียกคิวพร้อมกัน
  * `staff_labubu` (Role: `BOX_MASTER`, ซีรีส์: `LAB`): พนักงานประจำซีรีส์ Labubu ใช้ทดสอบการห้ามข้ามซีรีส์ (`FORBIDDEN_SERIES`)
* **A-04 (Real-time Strategy):** ใน Sprint 1 ถึง 3 ระบบเลือกใช้ Short Polling ทุก 3 วินาที ในการอัปเดตข้อมูลหน้าเว็บ ไม่ใช้ SSE หรือ WebSocket เพื่อลดความซับซ้อนของโครงสร้างพื้นฐาน
* **A-05 (Authentication & Token Lifecycle):** ใช้ JWT Token (HS256) มีอายุการใช้งาน 8 ชั่วโมง จัดเก็บใน `localStorage` ของเบราว์เซอร์ และส่งผ่าน `Authorization: Bearer <token>` มีกลไกการเพิกถอน Token ทันทีเมื่อ Logout ผ่านการอัปเดตฟิลด์ `tokenVersion` ในตารางผู้ใช้
* **A-06 (Sprint 1 Operational Limitation):** เนื่องจาก Sprint 1 ยังไม่มีฟังก์ชัน Cancel และ No-Show หากผู้ทดสอบกดเรียกคิวจนพนักงานติดสถานะ `CALLED` จะต้องรันสคริปต์ `npm run db:reset-demo` เพื่อเคลียร์สถานะสำหรับการทดสอบรอบถัดไป
* **A-07 (Single Day Operation):** ระบบออกแบบสำหรับการเข้าคิวภายในวันเดียวกันเท่านั้น ตั๋วคิวที่ค้างข้ามคืนจะไม่ถูกยกเลิกอัตโนมัติ โดยถือเป็น Known Limitation ของ Baseline ระบบ
